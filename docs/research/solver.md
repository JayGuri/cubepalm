# The solver, measured

> Generated by `npm run research` (`research/solver.study.ts`). Do not edit by hand: change the experiment and run it again.

CubePalm solves the cube with a two-phase (Kociemba-style) search that keeps improving its answer, plus a whole-cube search that can prove an answer is the shortest (`src/core/solvers/twoPhase.ts`). This report measures how long its tables take to build, how short its routes are on uniformly random cubes at several time budgets, how often it can prove a route optimal as the cube gets further from solved, and checks every route it produced against an independent cube implementation.

## Parameters

- seed: 20261011
- random states: 50 (uniform over all reachable cubes, from the seeded generator; chosen so the 5 s budget takes about four minutes in total)
- time budgets: 0.1 s, 0.5 s, 2 s, 5 s
- near-solved positions: 20 for each of 13 depths (2 to 14 random face turns)
- near-solved budgets: two-phase 0.3 s, proof 2 s
- machine: 12th Gen Intel(R) Core(TM) i7-12650H, 16 logical cores, win32 x64
- runtime: Node v20.19.3, one thread

## Building the tables

Milliseconds, 5 runs, each on a freshly loaded copy of the solver module. Run 1 includes the engine compiling the code. The runs can differ by a factor of two, and the later ones are not reliably faster than the first: each reload leaves the previous copy of the tables in memory for the garbage collector, and the cause of the spread has not been isolated. Read the figures as a range, not as one number.

| tables | run 1 | run 2 | run 3 | run 4 | run 5 | fastest | median |

| two-phase tables (6 move tables, 5 pruning tables) | 1528 | 2462 | 2717 | 4105 | 2755 | 1528 | 2717 |
| proof tables (3 move tables, 3 pruning tables) | 644 | 1443 | 1428 | 1266 | 1219 | 644 | 1266 |

## Correctness

Every route produced above (460 of them: each random state at each budget, and each near-solved position) was applied after its scramble in cubing.js, an independent implementation of the cube. 460 left the cube solved; 0 did not.

## What this does and does not show

- One machine, Node rather than a browser, one thread. The app runs the same code in web workers and splits the six views across up to four of them, so its timings differ. Costs "after t" depend on machine speed; "first answer" costs do not.
- 50 random states is a small sample: the means carry sampling error, and the minimum and maximum say little about the rarest cubes.
- The random states are uniform over all reachable cubes (see `docs/research/scrambles.md`), so the route costs describe typical scrambles, not hard positions chosen on purpose.
- "k random face turns" is not "distance k": turns can cancel, so some positions are closer to solved than k. The mean cost column shows the real distance wherever the route was proven.
- "Proven" rests on the arguments in `docs/MATH.md` (the lower bounds never over-estimate, the search is complete). The cubing.js check confirms that each route solves its cube; it cannot confirm that a route is the shortest.
- Timings were taken once per position, with nothing else deliberately running, but an ordinary desktop is not a quiet benchmark machine.
